# Groq API

Researched 2026-08-21 against Groq's own docs, the npm registry and the `groq/groq-typescript` source. No blog posts, no secondary write-ups. Every claim below links to the page that owns it. Where the docs are silent, it says so.

## What to do

Use the native `groq-sdk` package, currently `1.5.0`. Groq says out loud that it prefers its own library over the OpenAI one, and the native SDK is the only path that ships Groq's own types for Groq-only fields like `executed_tools` and `x_groq`.

For JSON extraction use `openai/gpt-oss-120b` with `response_format: { type: "json_schema", json_schema: { name, strict: true, schema } }`. It is one of exactly two models that support `strict: true`, and strict mode is the only mode Groq will say cannot produce invalid JSON. `qwen/qwen3.6-27b` and both `groq/compound` systems cannot do `json_schema` at all, only the older `json_object` mode.

Three things will break a naive 8 second budget, and all three are configuration, not luck:

1. The SDK's default per-request timeout is 60 seconds, not 8.
2. The SDK retries twice by default, and a timed-out request is one of the things it retries. Worst case is three 60 second waits plus backoff.
3. On a 429 the SDK reads the `retry-after` header and sleeps for exactly that long before retrying. Groq only sends `retry-after` on a 429, and the free tier's daily caps are low enough to hit, so that sleep can be long.

The safe shape for a cached-fallback design is `timeout: 8000, maxRetries: 0` and your own `AbortSignal`, with the fallback in the same function as the call. See section 5.

## 1. Package, version, and which SDK path Groq recommends

The package is `groq-sdk`. Latest published version is **1.5.0**, published 2026-07-31, from the npm registry metadata at `https://registry.npmjs.org/groq-sdk`. It has zero runtime dependencies. The repository is <https://github.com/groq/groq-typescript>. The library is generated by Stainless.

Groq publishes both paths and states a preference. On the OpenAI compatibility page: "We also have our own Groq Python and Groq TypeScript libraries that we encourage you to use." Source: <https://console.groq.com/docs/openai>

So: native `groq-sdk` is the recommended path. The OpenAI compat path exists so an existing OpenAI app can be repointed with two lines, not as the preferred way to start.

### Native SDK, server side

Install with `npm install --save groq-sdk` (the command Groq's own libraries page gives). The client reads `GROQ_API_KEY` from the environment by default, so the `apiKey` line can be dropped.

```ts
import Groq from "groq-sdk";

const groq = new Groq({ apiKey: process.env.GROQ_API_KEY });

const completion = await groq.chat.completions.create({
  model: "openai/gpt-oss-120b",
  messages: [
    { role: "system", content: "Extract the spatial clue from this survey passage." },
    { role: "user", content: passage },
  ],
});

const text = completion.choices[0]?.message?.content ?? "";
```

Source: <https://console.groq.com/docs/libraries> and the repository README at <https://github.com/groq/groq-typescript>.

### OpenAI SDK pointed at the compat base URL

Groq's own JavaScript snippet on the compatibility page:

```ts
import OpenAI from "openai";

const client = new OpenAI({
  apiKey: process.env.GROQ_API_KEY,
  baseURL: "https://api.groq.com/openai/v1"
});
```

Then call it exactly as you would call OpenAI:

```ts
const completion = await client.chat.completions.create({
  model: "openai/gpt-oss-120b",
  messages: [{ role: "user", content: passage }],
});
```

Source: <https://console.groq.com/docs/openai>

### Are the `openai` package types good enough?

Yes for the common path. Groq's wire format is the OpenAI chat completions format, the base URL is a drop-in, and the request and response shapes for `model`, `messages`, `response_format`, `choices`, `usage` and `finish_reason` all line up. The `openai` types will compile against Groq.

They stop being accurate where Groq adds fields OpenAI does not have. The documented Groq response carries `x_groq: { id: "req_..." }` and a richer `usage` object with `queue_time`, `prompt_time`, `completion_time` and `total_time`. The compound systems add `executed_tools` on the message. None of those exist in OpenAI's types. Going the other way, Groq's `ChatCompletion.Choice.finish_reason` is typed `'stop' | 'length' | 'tool_calls' | 'function_call'` with no `content_filter`, and the Groq message type has no `refusal` field, both of which OpenAI's types do have. Sources: <https://console.groq.com/docs/api-reference>, <https://console.groq.com/docs/compound>, and `src/resources/chat/completions.ts` in <https://github.com/groq/groq-typescript>.

### Documented unsupported OpenAI parameters

Verbatim from the compatibility page, under "Currently Unsupported OpenAI Features".

Text completions, "currently not supported and will result in a 400 error (yikes) if they are supplied":

- `logprobs`
- `logit_bias`
- `top_logprobs`
- `messages[].name`
- If `N` is supplied, it must be equal to 1.

Temperature: "If you set a `temperature` value of 0, it will be converted to `1e-8`." Groq suggests a float32 value greater than 0 and at most 2.

Audio transcription and translation: `vtt` and `srt` output values are not supported.

One more that only shows up in the API reference: `presence_penalty` is documented with the note "This is not yet supported by any of our models."

Sources: <https://console.groq.com/docs/openai> and <https://console.groq.com/docs/api-reference>

## 2. Structured outputs

Yes, Groq supports `response_format: { type: "json_schema", json_schema: { name, schema, strict: true } }`. There are three tiers, and Groq's own comparison table is the clearest statement of the difference.

|  | Strict Mode | Best-effort Mode | JSON Object Mode |
| --- | --- | --- | --- |
| Valid JSON | Always | Usually | Usually |
| Schema adherence | Guaranteed | Best-effort | No |
| Can error | No | Occasionally | Occasionally |
| Requires schema | Yes | Yes | No |
| Model support | Multiple models | Multiple models | All models |

With `strict: true` the model "uses **constrained decoding** to guarantee that the output will always match your schema exactly". Groq describes it as never producing invalid JSON, because "the model is constrained at the token level to only generate valid outputs".

With `strict: false`, which is the default when you omit the field, the model "attempts to match your schema but without hard constraints". It may produce valid JSON with the wrong field types or missing fields, may produce malformed JSON, and may trigger 400 errors.

`json_object` mode is weaker still. It is "basic JSON output validation without schema enforcement", designed to produce valid JSON syntax and nothing more. It takes no schema. Groq requires that you "include explicit JSON instructions in your prompt (system message or user input)" or the model will not emit JSON, and the SDK type carries the same warning: "the model will not generate JSON without a system or user message instructing it to do so."

Source for all of the above: <https://console.groq.com/docs/structured-outputs>

### The TypeScript call

Groq's own example, from the same page:

```ts
import Groq from "groq-sdk";

const groq = new Groq();

const response = await groq.chat.completions.create({
    model: "openai/gpt-oss-20b",
    messages: [
        { role: "system", content: "You are a helpful math tutor. Guide the user through the solution step by step." },
        { role: "user", content: "how can I solve 8x + 7 = -23" }
    ],
    response_format: {
        type: "json_schema",
        json_schema: {
            name: "math_response",
            strict: true,
            schema: {
                type: "object",
                properties: {
                    steps: {
                        type: "array",
                        items: {
                            type: "object",
                            properties: {
                                explanation: { type: "string" },
                                output: { type: "string" }
                            },
                            required: ["explanation", "output"],
                            additionalProperties: false
                        }
                    },
                    final_answer: { type: "string" }
                },
                required: ["steps", "final_answer"],
                additionalProperties: false
            }
        }
    }
});
```

### The `json_schema` object

From the SDK's generated types in `src/resources/chat/completions.ts`:

- `name` is required. "Must be a-z, A-Z, 0-9, or contain underscores and dashes, with a maximum length of 64."
- `description` is optional and is "used by the model to determine how to respond in the format", so it is a real prompt surface, not decoration.
- `schema` is optional in the type but is the point of the feature.
- `strict` is `boolean | null` and optional. Omitted means best-effort.

Source: <https://github.com/groq/groq-typescript/blob/main/src/resources/chat/completions.ts>

### Documented schema constraints

Supported types, verbatim: primitives are String, Number, Boolean, Integer. Complex types are Object, Array, Enum. Composition is `anyOf` only. Groq calls the whole thing "a JSON Schema subset with specific constraints for performance and reliability".

Under `strict: true` the constraints are mandatory:

- **Every property must be in `required`.** "All schema properties must be marked as `required`. Optional fields are not supported."
- **Every object must set `additionalProperties: false`.** "All objects must set `additionalProperties: false` to prevent undefined properties."
- **Optional values are expressed as a null union**, not by omission from `required`: `{ "type": ["string", "null"] }`, with the field still listed in `required`.
- **Each branch of an `anyOf` must itself obey the whole subset**, including its own `additionalProperties: false` and its own complete `required` list.
- **Recursion works**, both as `{ "$ref": "#" }` for self-reference at the root and through `$defs` with `{ "$ref": "#/$defs/name" }`.

Under `strict: false`: optional fields are allowed, `additionalProperties` "can be `true` or omitted (though `false` is recommended)", and validation is best-effort. Groq's own note: "While `strict: false` is more flexible, following the `strict: true` requirements will improve output quality and reduce validation errors."

Two hard restrictions that apply to structured outputs generally: "Streaming and tool use are not currently supported with Structured Outputs."

**Unverified.** Groq's docs do not publish a maximum nesting depth, a maximum number of enum values, a maximum property count, a total schema size limit, or an explicit list of rejected JSON Schema keywords such as `minLength`, `maxLength`, `pattern`, `minimum`, `maximum` or `format`. The only statement is the general one that a subset is supported and the positive list of what is in it. Anything narrower than that list is a guess. Do not assume `pattern` or `format` are enforced; validate on our side.

Source: <https://console.groq.com/docs/structured-outputs>

### Failure modes

**Strict mode.** Groq's position is that there is nothing to handle: "Constrained decoding guarantees schema-compliant output, so you won't encounter schema validation errors." Its own example carries the comment "Simple and reliable - no try/catch needed for validation". The one caveat it does give is that strict mode is model-limited and "If you run into 400 errors, we'd appreciate repros posted to our developer forum", which is an admission that a 400 is still reachable.

**Best-effort mode.** "Schema validation failures may occur and return HTTP 400 errors with the message `Generated JSON does not match the expected schema. Please adjust your prompt.`" Groq's suggested responses are retry, refine the prompt, simplify the schema, or move to `strict: true`.

**The 400 body itself** follows the standard Groq error object:

```json
{
  "error": {
    "message": "String - description of the specific error",
    "type": "invalid_request_error"
  }
}
```

Source: <https://console.groq.com/docs/errors>

**Truncation.** `finish_reason` is `'stop' | 'length' | 'tool_calls' | 'function_call'`, and `length` means "the maximum number of tokens specified in the request was reached". So a schema too large for the output budget comes back as `finish_reason: "length"` with truncated content in `message.content`. Groq does not say anywhere what strict mode's constrained decoding does when it runs out of tokens mid-object, and it does not claim that a `length` finish still yields parseable JSON. **Treat this as unverified and check `finish_reason === "stop"` before parsing.** For sizing: `openai/gpt-oss-120b` has a 131,072 token context window and a 65,536 max output tokens; `qwen/qwen3.6-27b` has 131,072 context and 16,384 max output.

**Refusals.** Groq lists "Programmatic refusal detection: Detect safety-based model refusals programmatically" as a benefit of structured outputs, and repeats the phrase in the introduction. That is the whole of it. **Unverified and, on the evidence, probably not true in the OpenAI sense:** unlike OpenAI, the Groq SDK's chat completion message type has no `refusal` field, and `finish_reason` has no `content_filter` value. There is no documented response shape for a refusal. Assume a refusal arrives as ordinary content that happens to fit the schema, and design the schema so a refusal is representable (an explicit null or an empty-result branch) rather than expecting a separate signal. Groq's own best practice points the same way: "Include explicit instructions for invalid or incompatible inputs. Models attempt schema adherence even with unrelated data, potentially causing hallucinations. Specify fallback responses (empty fields, error messages) for incompatible inputs."

Sources: <https://console.groq.com/docs/structured-outputs>, <https://console.groq.com/docs/errors>, <https://console.groq.com/docs/model/openai/gpt-oss-120b>

### The compound systems specifically

`groq/compound` and `groq/compound-mini` are agentic systems, not models. Groq describes compound as "an advanced AI system that is designed to solve problems by taking action and intelligently uses external tools, such as web search and code execution, alongside the powerful GPT-OSS 120B, Llama 4 Scout, and Llama 3.3 70B models". `groq/compound` supports multiple tool calls per request; `groq/compound-mini` supports a single one and has "an average of 3x lower latency". Both run their tools server side, and "Custom user-provided tools are not supported at this time."

They do accept `response_format`, but only the `json_object` form. Both system cards list their capabilities as "Web Search, Code Execution, Visit Website, Wolfram Alpha, JSON Object Mode", and the JSON Object Mode link points at the `#json-object-mode` anchor of the structured outputs page, not at the page itself. Neither card lists JSON Schema Mode. So `response_format: { type: "json_object" }` is accepted and `response_format: { type: "json_schema", ... }` is not offered for them.

Two other things worth knowing before reaching for compound: its rate limits are not its own, "Rate limits for `groq/compound` are determined by the rate limits of the individual models that comprise them", and its built-in tools are billed separately from tokens, for example basic web search at $5 per 1000 requests and Visit Website at $1 per 1000 requests.

Sources: <https://console.groq.com/docs/compound>, <https://console.groq.com/docs/compound/systems/compound>, <https://console.groq.com/docs/compound/systems/compound-mini>

Groq's own caveats on that table: "The following is a high level summary and there may be exceptions to these limits", and the exact numbers for an account live at <https://console.groq.com/settings/limits>.

Four things about how the limits behave:

- Limits apply per organization, not per user or per key.
- You hit whichever limit you reach first. Groq's example: "Let's say your RPM = 50 and your TPM = 200K. If you were to send 50 requests with only 100 tokens within a minute, you would reach your limit even though you did not send 200K tokens."
- "Cached tokens do not count towards your rate limits."
- Some organizations also get separate ITPM and OTPM caps on top of the combined TPM. If a breakdown appears next to the TPM value on the limits page you have them; if not, there is a single combined cap.

For our purposes, the binding number is **8K TPM on `openai/gpt-oss-120b`**. Prompt plus completion, across the whole organization, per minute. A single archival passage extraction with a long system prompt can be a meaningful fraction of that, and two or three concurrent ones will 429.

Source: <https://console.groq.com/docs/rate-limits>

### The 429 and its headers

Groq documents the status but not a body specific to 429: "When you exceed rate limits, our API returns a `429 Too Many Requests` HTTP status code." No 429-specific example body is published. The generic error object from the errors page is the shape to expect:

```json
{
  "error": {
    "message": "String - description of the specific error",
    "type": "invalid_request_error"
  }
}
```

**Unverified:** the exact `message` text and `type` value for a rate limit 429. Do not match on the string.

Headers, verbatim from the rate limits page, with Groq's own illustrative values and notes:

| Header | Value | Notes |
| --- | --- | --- |
| retry-after | 2 | In seconds |
| x-ratelimit-limit-requests | 14400 | Always refers to Requests Per Day (RPD) |
| x-ratelimit-limit-tokens | 18000 | Always refers to Tokens Per Minute (TPM) |
| x-ratelimit-remaining-requests | 14370 | Always refers to Requests Per Day (RPD) |
| x-ratelimit-remaining-tokens | 17997 | Always refers to Tokens Per Minute (TPM) |
| x-ratelimit-reset-requests | 2m59.56s | Always refers to Requests Per Day (RPD) |
| x-ratelimit-reset-tokens | 7.66s | Always refers to Tokens Per Minute (TPM) |

Two details that matter. The reset headers are Go duration strings like `2m59.56s`, not seconds and not a timestamp, so they need parsing rather than `Number()`. And `retry-after` is conditional: "`retry-after` is only set if you hit the rate limit and status code 429 is returned. The other headers are always included."

Note what the request-count headers do **not** cover. `x-ratelimit-limit-requests` "always refers to Requests Per Day", so there is no header telling you how much of the 30 RPM budget is left. Per-minute request pacing has to be tracked on our side.

To read the headers with the native SDK, use `.withResponse()`:

```ts
const { data, response } = await groq.chat.completions
  .create({ model: "openai/gpt-oss-120b", messages })
  .withResponse();

const tokensLeft = response.headers.get("x-ratelimit-remaining-tokens");
```

Sources: <https://console.groq.com/docs/rate-limits>, <https://console.groq.com/docs/errors>, <https://github.com/groq/groq-typescript>

## 5. Timeouts, cancellation and retries

All of this is from the `groq-typescript` README and the client source, which agree.

### Per-request timeout

Default is 60 seconds. From the README: "Requests time out after 1 minute by default." Confirmed in the source as `static DEFAULT_TIMEOUT = 60000; // 1 minute`. Set it on the client, per request, or both.

```ts
// client default
const groq = new Groq({ timeout: 20 * 1000 });

// per request, wins over the client default
await groq.chat.completions.create(
  { model: "openai/gpt-oss-120b", messages },
  { timeout: 5 * 1000 },
);
```

On timeout the SDK throws `APIConnectionTimeoutError`, which extends `APIConnectionError`, which extends `APIError`, which extends `GroqError`. Its `status`, `headers` and `error` are all `undefined` and its message is "Request timed out."

The trap, stated by Groq in the README: "Note that requests which time out will be retried twice by default." The client source spells out the consequence: "request timeouts are retried by default, so in a worst-case scenario you may wait much longer than this timeout before the promise succeeds or fails."

### AbortSignal

`signal` is a per-request option on every method, typed `AbortSignal | undefined | null` and documented in the source as "An AbortSignal that can be used to cancel the request." It is passed straight through to `fetch`.

```ts
const controller = new AbortController();
const kill = setTimeout(() => controller.abort(), 8000);

try {
  const completion = await groq.chat.completions.create(
    { model: "openai/gpt-oss-120b", messages },
    { signal: controller.signal, timeout: 8000, maxRetries: 0 },
  );
  return parse(completion);
} catch {
  return cachedFallback;
} finally {
  clearTimeout(kill);
}
```

An aborted request surfaces as `APIUserAbortError`, message "Request was aborted.", also with `status`, `headers` and `error` undefined. It is a different class from `APIConnectionTimeoutError`, so the two are distinguishable if you need to be.

### Retries

Default is 2. From the README: "Certain errors will be automatically retried 2 times by default, with a short exponential backoff. Connection errors (for example, due to a network connectivity problem), 408 Request Timeout, 409 Conflict, 429 Rate Limit, and >=500 Internal errors will all be retried by default."

The source confirms the exact rule. `shouldRetry` returns true for 408, 409, 429 and anything at or above 500, plus connection and timeout failures. It also honours a non-standard `x-should-retry` header from the server in either direction, which overrides the status rule.

Backoff is 0.5 seconds doubling to a cap of 8 seconds, with up to 25 percent jitter subtracted. **But that only applies when the server does not tell it otherwise.** The SDK first looks for `retry-after-ms`, then `retry-after`, and if either is present it sleeps for exactly that long instead of using its own backoff. The source comment: "If the API asks us to wait a certain amount of time, just do what it says, but otherwise calculate a default." Since Groq sends `retry-after` on every 429, a 429 retry sleeps for however long Groq asks.

Disable retries, or raise them, on the client or per request:

```ts
const groq = new Groq({ maxRetries: 0 }); // default is 2

await groq.chat.completions.create(
  { model: "openai/gpt-oss-120b", messages },
  { maxRetries: 5 },
);
```

Error classes for reference, from the README:

| Status Code | Error Type |
| --- | --- |
| 400 | `BadRequestError` |
| 401 | `AuthenticationError` |
| 403 | `PermissionDeniedError` |
| 404 | `NotFoundError` |
| 422 | `UnprocessableEntityError` |
| 429 | `RateLimitError` |
| >=500 | `InternalServerError` |
| N/A | `APIConnectionError` |

`APIError` carries `status`, `headers` and `error`, so a `RateLimitError` gives you the `retry-after` and `x-ratelimit-*` headers directly off the caught object.

Sources: <https://github.com/groq/groq-typescript> README, `src/client.ts`, `src/core/error.ts`, `src/internal/request-options.ts`

## What the docs do not answer

Listed together so none of it gets mistaken for fact later.

- No published maximum schema nesting depth, enum count, property count or schema size for structured outputs.
- No explicit list of JSON Schema keywords that are rejected or silently ignored. Only a positive list of what is supported.
- No documented behaviour for strict mode when generation hits the output token cap mid-object, and no promise that a `finish_reason: "length"` response is parseable.
- No response field or `finish_reason` value that identifies a refusal, despite "programmatic refusal detection" being listed as a benefit.
- No 429-specific response body example, so the `message` and `type` strings for a rate limit error are unknown.
- No published latency figures per model beyond a rough tokens-per-second number on each model card, so an 8 second budget cannot be justified from the docs. It has to be measured.
